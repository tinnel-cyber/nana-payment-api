1. Présentation de NanaSwitch Cloud & Mission B2B

NanaSwitch Cloud est l'orchestrateur de paiement intelligent de référence en Afrique de l'Ouest. Développé et opéré par l'entité NANASORE TECHNOLOGIES, il résout le problème critique de la fragmentation des passerelles de paiement locales en fournissant une API unifiée haute disponibilité, compatible avec les principaux opérateurs Mobile Money et les cartes bancaires internationales.

2. Explication des Deux Modes d'Opération (Agrégé vs BYOK)

Mode Agrégé (Master Merchant) Commissions

NanaSwitch gère l'ensemble des flux financiers via son compte maître de régulation. Le marchand n'a besoin d'aucun contrat direct avec les opérateurs télécoms.

  • • Tarification : Frais opérateur de base + 1.5% de marge de switch retenue à la source.
  • • Disponibilité : Solde crédité instantanément sur le wallet NanaSwitch multi-devises (XOF, USD, XAF, GNF, GHS) avec payout à la demande.
  • • Plafonds mensuels KYC stricts :
    • Particulier / Indépendant : max 1 000 000 XOF/mois (CNIB + Selfie).
    • Entreprise Enregistrée : max 5 000 000 XOF/mois (RCCM + IFU + CNIB).
Mode BYOK (Bring Your Own Key) Routeur SaaS

Conçu pour les FinTechs, entrepreneurs, e-commerçants, startups et grandes entreprises qui possèdent déjà leurs propres clés d'API délivrées dans le cadre d'un contrat direct entre eux et leurs agrégateurs ou opérateurs de paiement (Orange Money, MTN MoMo, Moov Africa, Wave Business, SasPay, Sebpay, banques partenaires, etc.).

  • • Gestion des fonds : Routage direct pass-through. Les fonds vont directement sur vos comptes marchands. NanaSwitch ne touche pas à l'argent et ne stocke aucun fonds.
  • • Tarification SaaS : 0% de commission de switch. Facturation SaaS à 0,02 XOF par requête / transaction débité de vos crédits API.
  • • Plafonds de volume : Exempt de tout plafond de volume (Transactions illimitées sans restriction mensuelle).
  • • Responsabilité : Vos clés privées restent sous votre entière responsabilité et sont injectées via notre coffre-fort Zero-Trust.

Dictionnaire Technique, Modèle Zero-Trust & Conseils de Gestion

Rôle : Cybersecurity & Technical Content Specialist. Glossaire fondamental, architecture des clés et hygiène financière.

1 Glossaire des Termes Techniques

Mode Agrégé (Master Merchant) Compte Maître Régulé

Modèle tout-en-un où NanaSwitch opère comme Maître Marchand. Aucun contrat préalable avec les opérateurs n'est requis. NanaSwitch encaisse sur ses comptes régulés, retient sa marge (+1.5% de frais de switch à la source) et crédite directement le Wallet du marchand. Ce mode est soumis aux plafonds stricts de vérification d'identité KYC (1 000 000 XOF/mois pour Particulier, 5 000 000 XOF/mois pour Entreprise).

BYOK (Bring Your Own Key)

Usage direct de ses propres clés d'accès API délivrées par contrat direct entre le marchand / fintech et ses opérateurs partenaires. NanaSwitch agit comme routeur SaaS pur (0% commission, 0,02 XOF/requête).

HMAC-SHA256

Signature cryptographique symétrique (Hash-based Message Authentication Code) garantissant l'inviolabilité absolue des webhooks et l'authenticité de chaque notification d'encaissement.

Failover / Smart Routing

Routage dynamique automatique vers un agrégateur ou corridor de secours en cas d'indisponibilité d'un opérateur (ex: optimisation et forçage de l'indicatif +226 au Burkina Faso).

Idempotence (Idempotency Key)

Envoi de l'en-tête x-idempotency-key prévenant tout risque de double débit lors des retries réseau ou instabilités de connexion.

2 Architecture des Clés Zero-Trust

ns_live_pk_... Front-End

Clé Publique (Public Key)

Utilisée côté Client / Frontend (SDK Web, boutons de paiement, extensions e-commerce).

Sécurité : Peut être publique sans danger. Ne permet aucun retrait ni remboursement.

ns_live_sk_... Confidentiel

Clé Secrète (Secret Key)

À garder strictement confidentielle côté Serveur backend (Authorization: Bearer).

Interdiction : Jamais de commit sur GitHub ni d'exposition dans le code client React/JS.

ns_whsec_... HMAC-SHA256

Clé Secrète Webhook (Signing Secret)

Clé partagée servant à recalculer et authentifier l'en-tête de signature x-nanaswitch-signature.

Anti-rejeu : Tolérance stricte de 300 secondes (5 minutes) contre les attaques par rejeu.

3 Conseils de Gestion Financière & Révocation d'Urgence

Rotation d'Urgence (Fuite de Clé)

En cas de compromission, régénérez vos clés depuis le dashboard. L'ancienne clé bénéficie d'une période de grâce de 24h pour permettre la bascule de vos serveurs de production sans coupure de service.

Stockage & Secrets Management

Conservez vos clés dans des variables d'environnement (.env) obligatoirement incluses dans votre .gitignore, ou utilisez des vaults managés (AWS Secrets Manager, GCP Vault).

Réconciliation de Trésorerie

Rapprochez quotidiennement les webhooks payment.success reçus et les soldes de vos wallets multi-devises pour anticiper les plafonds de volume KYC et auditer les flux.

Implémentation de Référence : Vérification Cryptographique Timing-Safe (Node.js) 
const crypto = require('crypto');

function verifyNanaSwitchWebhook(rawBody, signatureHeader, webhookSecret) {
  if (!signatureHeader || !webhookSecret) return false;

  const parts = Object.fromEntries(
    signatureHeader.split(',').map(pair => pair.trim().split('='))
  );

  const timestamp = parseInt(parts.t, 10);
  const signature = parts.v1;

  // 1. Fenêtre anti-rejeu stricte de 300 secondes (5 min)
  if (Math.abs(Date.now() / 1000 - timestamp) > 300) {
    throw new Error('SECURITY_ERROR: Webhook timestamp expired (> 300s)');
  }

  // 2. Calcul du HMAC-SHA256 sur "${timestamp}.${rawBody}"
  const expected = crypto
    .createHmac('sha256', webhookSecret)
    .update(`${timestamp}.${rawBody}`)
    .digest('hex');

  // 3. Comparaison en temps constant (timingSafeEqual)
  return crypto.timingSafeEqual(Buffer.from(signature, 'utf8'), Buffer.from(expected, 'utf8'));
}

2. Vérification Webhook HMAC-SHA256 (timingSafeEqual) 
// Verification Webhook HMAC-SHA256
function verifyWebhook(payload, signatureHeader, secret) {
  const [timestamp, signature] = signatureHeader.split(',');
  const tsValue = timestamp.split('=')[1];
  const sigValue = signature.split('=')[1];
  
  const expectedSig = crypto
    .createHmac('sha256', secret)
    .update(`${tsValue}.${payload}`)
    .digest('hex');
    
  return crypto.timingSafeEqual(Buffer.from(sigValue), Buffer.from(expectedSig));
}

2. Vérification Webhook HMAC-SHA256 (Python) 
# Verification Webhook HMAC-SHA256 (Python)
import hmac
import hashlib

def verify_webhook(payload: str, signature_header: str, secret: str) -> bool:
    try:
        parts = dict(part.strip().split('=') for part in signature_header.split(','))
        ts_value = parts.get('t')
        sig_value = parts.get('v1')
        
        if not ts_value or not sig_value:
            return False
            
        signed_payload = f"{ts_value}.{payload}".encode('utf-8')
        expected_sig = hmac.new(
            secret.encode('utf-8'),
            signed_payload,
            hashlib.sha256
        ).hexdigest()
        
        return hmac.compare_digest(sig_value, expected_sig)
    except Exception:
        return False
3. Serveur Webhook de Référence (FastAPI) 
from fastapi import FastAPI, Request, HTTPException
import json
import os

app = FastAPI()
WEBHOOK_SECRET = os.getenv("NANASWITCH_WEBHOOK_SECRET", "ns_whsec_...")

@app.post("/api/webhook")
async def handle_webhook(request: Request):
    sig_header = request.headers.get("x-nanaswitch-signature")
    body_bytes = await request.body()
    body_str = body_bytes.decode("utf-8")

    if not verify_webhook(body_str, sig_header, WEBHOOK_SECRET):
        raise HTTPException(status_code=401, detail="Invalid signature")

    event = json.loads(body_str)
    if event.get("event_type") == "payment.success":
        print(f"Paiement validé : {event.get('order_id')} ({event.get('amount')} XOF)")

    return {"received": True}
